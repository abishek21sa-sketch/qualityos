# QualityOS database starting point

`schema.sql` is the reviewed PostgreSQL starting point for replacing the browser/file-backed prototype. It models workspace membership, suppliers, parts, lots, inspections, signals, NCRs, containment, corrective actions, CAPA effectiveness, evidence metadata, and audit events.

`postgres-store.mjs` is the optional workspace-state adapter. Set `DATABASE_URL` to enable it; otherwise the Node API continues using its file-backed adapter. It stores versioned workspace JSON and synchronizes corrective actions, CAPAs, inspections, evidence metadata, and audit events into normalized tables in the same transaction. Reads and ETag checks use the same canonical merged workspace, including empty normalized collections. Inspection migration resolves workspace parts and lots and preserves SPC/UI fields in `metadata`. Evidence request metadata is relational; browser attachment bytes remain in the workspace bridge until object storage is added. Audit events use stable source keys and are inserted append-only; clearing a browser's shorter event list does not delete the server audit copy.

Run `npm run db:migrate` to initialize or upgrade the database. On an empty database, the migration runner applies `schema.sql` transactionally; when it detects an existing QualityOS schema, it records the baseline without replaying the type/table creation statements. It then applies pending SQL files transactionally, serializes concurrent startup migrations with a PostgreSQL advisory lock, and records each step in `qualityos_schema_migrations`. It safely does nothing when `DATABASE_URL` is not configured. Render runs this command before starting the API service. `npm test` also exercises the PostgreSQL workspace adapter and migration runner with fake query clients, covering canonical ETags, normalized-record persistence, append-only audit, clean bootstrap, existing-schema upgrades, idempotent runs, and rollback without needing a database credential.
