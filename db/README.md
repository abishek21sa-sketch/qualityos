# QualityOS database starting point

`schema.sql` is the reviewed PostgreSQL starting point for replacing the browser/file-backed prototype. It models workspace membership, suppliers, parts, lots, inspections, signals, NCRs, containment, corrective actions, CAPA effectiveness, evidence metadata, and audit events.

`postgres-store.mjs` is the optional workspace-state adapter. Set `DATABASE_URL` to enable it; otherwise the Node API continues using its file-backed adapter. The adapter expects `schema.sql` to have been applied, stores the versioned workspace JSON in `workspace_state`, and performs a row lock plus ETag check inside a transaction. Corrective actions, CAPAs, inspections, and evidence metadata are synchronized into the normalized `corrective_actions`, `capas`, `inspections`, and `evidence` tables in that same transaction. Inspection migration resolves workspace parts and lots and preserves SPC/UI fields in `metadata`. Evidence request metadata is now relational; browser attachment bytes remain in the workspace bridge until object storage is added.

Run `npm run db:migrate` to initialize or upgrade the database. On an empty database, the migration runner applies `schema.sql` transactionally; when it detects an existing QualityOS schema, it records the baseline without replaying the type/table creation statements. It then applies pending SQL files transactionally, serializes concurrent startup migrations with a PostgreSQL advisory lock, and records each step in `qualityos_schema_migrations`. It safely does nothing when `DATABASE_URL` is not configured. Render runs this command before starting the API service.
